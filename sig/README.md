# RBS sig files (benchmark workload for ruby/rbs)

This `sig/` directory is **not maintained type signatures** for GitLab.
It is a static-analysis snapshot generated by [`rbs prototype rb`][1] from
`app/`, `lib/`, and `gems/*/lib`, used as a large workload for benchmarking
the [ruby/rbs][2] resolver on Ruby 4.0+.

[1]: https://github.com/ruby/rbs/blob/master/docs/CLI.md#rbs-prototype
[2]: https://github.com/ruby/rbs

## Why this exists

`conference-app` (a few hundred `.rbs` files) is too small to surface the
performance differential of resolver-side optimizations. GitLab's
`app/` + `lib/` + `gems/` provides a much larger workload — currently:

- ~10,000 source `.rb` files
- ~11,600 generated `.rbs` files under `sig/`
- plus the gem RBS collection (Rails, ActiveSupport, Sidekiq, …) under
  `.gem_rbs_collection/`, so that GitLab's relative type references
  actually resolve (resolution success rate ~98% vs ~76% without it)

The hand-written content is intentionally rough (`untyped` everywhere);
the goal is to exercise resolver code paths, not to type-check GitLab.

## Layout

```
sig/                     prototype RBS for GitLab's own code
  app/ lib/ gems/
.gem_rbs_collection/     third-party gem RBS (from `rbs collection install`)
rbs_collection.yaml      collection config
rbs_collection.lock.yaml pinned collection versions
```

No GitLab source code (Gemfile included) was modified. The Gemfile does
**not** need to be made Ruby-4.0-compatible: `rbs collection install`
reads `Gemfile.lock` (gem names + versions) directly and never runs
`bundle install`.

## Quickstart

```bash
# 1. Shallow clone of this fork (full clone, NOT --filter=blob:none —
#    partial clones make `git push` re-fetch blobs and hang).
git clone --depth=1 https://github.com/tk0miya/gitlabhq.git
cd gitlabhq

# 2. (Re)install the gem RBS collection if .gem_rbs_collection is absent.
#    Force Ruby 4.0 because the repo's .ruby-version pins an older MRI.
RBS=/path/to/rbs/checkout
RBENV_VERSION=4.0.4 $RBS/exe/rbs collection install

# 3. Run the benchmark against any ruby/rbs branch. Load BOTH the
#    GitLab sigs and the gem collection so type names resolve.
ruby -I$RBS/lib -I$RBS/tmp/arm64-darwin24/stage/lib -rbenchmark -rrbs -e '
  loader = RBS::EnvironmentLoader.new
  Dir.glob(".gem_rbs_collection/*/*/").sort.each { |d| loader.add(path: Pathname(d)) }
  loader.add(path: Pathname("sig"))
  env = RBS::Environment.from_loader(loader)
  env = env.resolve_type_names              # 1st resolve: heavy
  15.times do                              # 2nd+: immutable-reuse path
    t = Benchmark.realtime { env = env.resolve_type_names }
    puts "%.2f ms" % (t * 1000)
  end
'
```

The benchmark chains `env = env.resolve_type_names` so the 2nd-and-later
resolves operate on the already-absolutized env — this is the path the
`resolve_type_names` decl-reuse optimization targets.

## Regenerating the sigs

```bash
RBS=/path/to/rbs/checkout            # needs the compiled C extension
cd /path/to/gitlabhq
$RBS/exe/rbs prototype rb --out-dir=sig/app --base-dir=app app
$RBS/exe/rbs prototype rb --out-dir=sig/lib --base-dir=lib lib
for g in gems/*/lib; do
  $RBS/exe/rbs prototype rb --out-dir="sig/gems/$(basename $(dirname $g))" --base-dir="$g" "$g"
done
```

`rbs prototype rb` parses with `RubyVM::AbstractSyntaxTree`, so it needs
MRI Ruby; jruby/truffleruby will not work.

## Caveats

- The hand-written sigs contain no real type information — method
  params/returns are all `untyped`. The point is resolver load, not
  type accuracy.
- `.gem_rbs_collection/` is committed for a self-contained, reproducible
  workload. Normally it is regenerable from the lock file, but pinning
  it here means the benchmark does not depend on the upstream
  `ruby/gem_rbs_collection` repo state or network access.
- Generated on Ruby 4.0.4 with `rbs` at master (June 2026).

## Baseline numbers

`rbs/master` vs optimization branches (`bardeen` = Namespace trie
inlining, `immutable` = `equal?`-based decl reuse in
`resolve_type_names`), chained 2nd+ resolves, median over 15 iterations,
with the gem collection loaded:

| Branch | 2nd+ wall median | 2nd+ allocations |
| --- | --- | --- |
| master | 354 ms | 1,232,837 |
| immutable alone | 288 ms | 584,154 (-53%) |
| bardeen alone | 307 ms | 1,077,330 (-13%) |
| bardeen + immutable | 276 ms | 428,698 (-65%) |

Apple Silicon, macOS Darwin 24.6, Ruby 4.0.4 (YJIT off). Wall-clock
variance is high on this machine; allocation counts are deterministic
and the more reliable signal.
